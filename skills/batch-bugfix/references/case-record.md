# 问题状态与机器输入

## 三个独立维度

| 维度 | 记录内容 |
|---|---|
| 证据 | 候选／静态路径确认／真实函数离线复现／隔离集成复现／真实环境观测；附基线、输入、输出、命令和环境 |
| 决策 | 影响、发生条件、优先级、产品预期、归属、当前启用情况、是否值得修 |
| 交付 | 待验证／确认／修复中／部分修复／审查通过／集成通过／已推送／PR/MR 已创建／已合并／已部署 |

用一条记录串联：`case_id → 原始报告 → 复现与正常对照 → 修复范围 → 审查链 → 测试证据 → 发布链接`。

离线函数有缺陷，并不证明线上已发生；明确拒绝不支持的格式，也可能满足原 Issue 的契约。按原预期核对，不擅自升级为功能开发。协议返回成功还需看调用者最终展示/持久化结果。

完整修复意味着本次接受的全部验收条件已满足。部分修复列出已满足项和仍失败项、原始复现结果、下一项所需决定。新增专项测试通过不能抵消原始复现仍失败；没有被选入套件的测试也不能被算作通过。范围外观察另列，不据此扩写修复结果。

## 修复准入

决定进入本批前，核对三个问题：哪条已确认契约被违反；当前版本的调用者、配置和支持输入能否到达该路径；不修会造成什么可观察影响。线上已发生不是必要条件，支持场景下的确定性复现可以成立；人为注入契约外输入，只证明该异常条件下的表现。只有明确的防御性需求或风险依据支持时，才将其纳入修复。

将理由记在现有问题记录中，选择本批修复、待补证据或暂不修复。必要性与严重度分别判断；证据不足的候选保留缺口，既不冒充已确认缺陷，也不从批次记录中消失。

## 验证范围

实现前沿用已确认的测试边界，为所选检查说明要回答的问题。优先复用既有用例；新增用例对应原始故障、正常行为或本改动引入的具体风险，预期来自契约或独立样例。参数组合只覆盖行为确有差异的条件；测试放在项目现有的对应职责位置，路径受限时先按仓库规则处理。

结果分开报告：原问题从失败到通过（FAIL_TO_PASS）、原有正常行为保持通过（PASS_TO_PASS）、已有失败及未验证项。新增回归用例尽可能在原基线证明会失败，在补丁上证明会通过；无法执行原基线时记录限制。原始调用场景仍失败时按部分修复交付。

检查强度随影响选择：局部修复以相关行为为主，涉及数据完整性、权限或并发时覆盖实际受影响的失败路径。仓库要求的检查仍执行。完成条件是本次验收已满足、相关回归有结论、剩余风险已记录；没有新变化或未解决疑点时停止重复验证。

## 提交清单

`check_patch_manifest.py` 接收 JSON，路径相对清单文件解析。SHA 必须完整，不使用随分支移动的短引用充当审查证据。

```json
{
  "version": 1,
  "repo": "../worktree",
  "target_ref": "refs/remotes/origin/main",
  "target_sha": "完整的目标提交哈希",
  "cases": [{
    "id": "case-001",
    "status": "ready",
    "base": "本条审查起点的完整哈希",
    "commits": ["原修复完整哈希", "跟进修复完整哈希"],
    "head_ref": "refs/heads/fix/case-001",
    "files": ["src/module.py", "tests/test_module.py"]
  }]
}
```

`ready`、`partial`、`blocked` 为本次发布候选状态。检查器报告 partial/blocked 并非完整就绪（非零退出），不会静默过滤。每条必须是从 base 出发的线性完整链；检查分支头、逐提交父节点、所有中间提交触及文件的并集。此工具不 fetch、不判断语义、不证明 cherry-pick 等价。先更新 remote ref，再固定清单；新基线的测试和复核完成后更新清单。重命名两端、先改后撤的文件也算触及范围。

## 回归快照

`compare_test_results.py` 比较 JSON 快照：

```json
{
  "version": 1,
  "target_sha": "两边共同的完整上游哈希",
  "revision": "本次受测提交的完整哈希",
  "environment": "团队约定的解释器、系统及依赖环境标识",
  "suite": "同一套件的实际选择条件",
  "tests": [{"id": "tests.test_sample::test_one", "outcome": "passed"}]
}
```

允许结果：passed、failed、error、skipped。非 passed 项必须带 `fingerprint`，来自脱敏后的失败原因或跳过原因；同名失败原因变化需要重查。已知基线失败必须保持身份与原因一致，且 baseline.revision 等于 target_sha。新增用例必须通过。失败/跳过转通过会列入 improvements；消失的测试、新增跳过或结果恶化返回非零。确有意删除/重命名用例时人工登记映射与理由，再更新测试选择；不要用总通过数覆盖差异。

JUnit 可转快照：

```text
python scripts/compare_test_results.py snapshot results.xml --target-sha SHA --revision SHA --environment ENV --suite SUITE --out snapshot.json
```

JUnit 的 ID 使用 classname + name，保留参数化后缀。跨文件重名、报告为空或只有套件错误时拒绝比较。失败指纹保留错误文本，仅规范化换行；时间戳、临时路径或 runner 差异会要求人工核对，不被默认为同一个基线失败。先确认 XML 对应实际运行及完整选择条件；文件存在不是测试运行证据。
