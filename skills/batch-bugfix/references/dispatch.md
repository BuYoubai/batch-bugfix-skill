# 分工与独立复核

每个工作单给足下列材料，避免执行者重新猜任务：

- 明确的 case/Issue 列表、原预期和证据入口；当前基线与运行环境。
- 本轮要达到的阶段、可改路径、其他维护者负责的范围、当前授权。
- 当前环境的分工配置；需要指定模型时按 [模型路由](model-routing.md) 选择模型、思考程度并说明理由，配置只随本工作流的子任务传递。
- 独立工作树/分支及成果路径；是否共享文件、真正依赖谁、并行限制。
- 回传：完整提交链、改动文件、复现前后结果、正常对照、未验证/未修项；已发布才附远端链接。

产品 bug 按可独立审查和撤回的范围提交，必要的回归测试随对应修复一起提交。纯测试维护（如夹具、导入或测试环境适配）积累为一批统一提交，不为每个小调整单独提交或推送；若它是验证本次修复的前提，则纳入本批，避免延误修复验收。对同一文件的改动先看语义关系，不凭文件重叠就制造堆叠依赖。受测工作树只消费冻结后的提交，不在作者正在变化的目录上集成。

让独立审查者看到原始契约、基线、补丁和运行方法；作者的“已通过”只作线索。审查者可选择不同反例，检查相似名字、空值、身份交叉、失败后恢复等与该改动相关的边界，并观察调用者输出。不要机械地给每项套全部边界。

返修由明确所有者处理，审查者复验后给出替换 SHA 或完整追加链。组合检查失败时先对照当前上游，区分产品回归、测试夹具失配和已有失败；夹具修复要调用真实当前协议，不能把返回值写死成成功。

并发任务间用小清单交接：`case_id / status / base / commits / report_path / remaining`。协调者主动读取完成结果；消息发送失败时保留本地成果并如实报告，不把“回传失败”算作“修复失败”。任务列表标题本身不证明交付完成。
