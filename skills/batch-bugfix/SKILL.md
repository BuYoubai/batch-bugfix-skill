# Batch bugfix

把一批问题推进到用户指定阶段，并保留每项的证据、范围和交付状态。本技能负责批次间的衔接，复用现有诊断、实现与审查能力。

## 从当前阶段进入

先核对本次目标、当前上游和已有产物，选下面的入口。已验证且基线未变的材料直接沿用；证据过期时只重做受影响部分。

| 当前材料 | 本次工作 | 完成条件 |
|---|---|---|
| 模块清单、怀疑点 | 建立候选，选择能观察到用户结果的路径；难定位的问题用 `diagnosing-bugs` | 每个候选有证据状态或具体缺口；进入修复前按下方准入条件作出决定 |
| 可复现的问题 | 用 [Issue 模板](assets/issue-evidence.md) 整理；对照远端已有问题再按授权提交 | 发布内容与证据一致，或留下可发布草稿 |
| 已确认范围的 Issue 或本地问题记录 | 核对预期、当前版本和责任范围，用 [分工契约](references/dispatch.md) 分组；实现时按需加载 `implement` / `tdd` | 每项完整或部分修复被明确记录 |
| 本地补丁 | 按下方复用条件接收已有 `code-review`，缺失时对固定提交执行；复核相关反例、正常对照及调用者，返修后更新提交链 | 审查意见闭环，形成冻结清单 |
| 多份已审补丁 | 运行 [提交清单检查器](scripts/check_patch_manifest.py)，在隔离工作树组合；按 [回归比较契约](references/case-record.md#回归快照) 对照当前上游 | 原有测试逐项可比，新增失败、消失用例和跳过均有裁决 |
| 待发布队列、发布中断 | 按下方“交付路径”核对授权、说明稿与远端状态，继续已选路径 | 目标分支 / PR/MR 回读通过，结果不明单列 |
| 跨任务续接 | 读取最后一份 [批次结果](assets/batch-result.md)，先确认上游、提交和远端有没有变化 | 从未完成阶段继续，不重复创建已发布对象 |

首次建台账或出现“这是否算修完”的分歧时读 [问题状态契约](references/case-record.md)。分组时读 [分工契约](references/dispatch.md)；确需委派时再读 [模型路由](references/model-routing.md)。业务预期仍不明确时只澄清会改变修复的那一项。文中命名的诊断、实现和审查技能均为可选增强：只有当前环境已安装并允许调用时才解析并完整读取；缺失时按项目既有流程执行，仍须保留复现、范围、规格/规范复核和验证证据。本技能可单独使用，不自动安装其他技能。

## 修复准入与技能交接

进入修复前，读取 [问题状态契约](references/case-record.md)，为每项记录契约依据、当前调用路径的可达性、不修的影响，以及“本批修复 / 待补证据 / 暂不修复”的理由。已获批量修复授权时由协调者据此决定；只有缺失的业务决定会改变范围时才询问用户。

使用 `implement` / `tdd` 前，传入已确认的规格、测试边界、可改范围和提交目标；沿用已有确认，只补充确实缺失的决定。按当前平台支持的方式解析并完整读取技能；用户调用型入口遵守平台调用规则，不改供应商元数据以强行调用。

接回补丁时，记录审查的 base/head SHA、规格与规范来源、两轴结论、未解决项及证据位置。`implement` 已完成的审查在这些条件仍适用时直接复用；缺失的审查轴或调用者证据补齐即可。返修和换基线只重查受影响范围，组合阶段重点检查补丁间交互及冲突处理；未变部分沿用已核验结果。冻结清单须覆盖最终差异，所有阻塞意见已处理。

选择验证范围与停止条件时，按状态契约中的“验证范围”执行。已有验证覆盖当前提交、环境和验收条件时继续交付；新变化或未解决疑点才扩大检查。

## 推进与停点

- 以用户的当前范围和已有授权推进。登记问题、修复、推送、创建 PR/MR、合并、部署分别记录授权；同一明确范围内持续授权有效，阶段变化不自动扩大授权。
- 分组依据独立业务契约和文件重叠，按真实依赖排序。用户要求新任务时创建用户可见任务；内部子任务只在当前规则允许委派时使用。没有必要就本地完成。
- 原提交后的跟进修复必须进入整条审查链。重放到新上游后，对照新旧差异，补查上游变化、冲突处理及受影响的行为；确认仍适用的审查和测试证据关联到新提交，保留旧 SHA 对照，再冻结发布 SHA。无需仅因 SHA 改变而全量重审。
- 在组合结果中保留原始未解决复现。专项全绿、部分修复和整个 Issue 完成都有各自含义；判断定义集中在状态契约。
- 同文件改动可独立提交，也可能互相依赖。真正堆叠的 PR/MR 明确前置与目标分支；上游或前序 PR/MR 变化后检查受影响差异。
- 批次大小随风险和审查能力调整。每批结束或中断后，用结果模板记录实际状态；只有真实新证据才刷新进度。

## 交付路径

进入交付准备或恢复发布时，读取 [交付执行](references/delivery.md)，按其中的最小交付规范准备说明、前后证据和风险；沿用用户已选路径、授权与停点。项目指定了外部 `pr` 技能时优先使用，缺失项按该项目规则处理。

| 路径 | 选择条件 | 完成条件 |
|---|---|---|
| MR / PR | 用户选择审查请求流程，并授权对应远端操作 | 说明写入远端正文；源/目标分支、SHA、正文和所授权阶段的状态回读一致 |
| 直接推入目标分支 | 用户明确授权本批范围直接推送指定远端分支，且仓库允许 | 保留本地交付说明，以普通非强制 push 写入精确目标；回读证明目标包含本批，记录提交链接 |

## 脚本入口

均只依赖 Python 3.10+ 标准库；Git 检查需要 git。发布时只读取对应平台说明：[GitHub](references/github.md) 使用已认证的 `gh`，[GitLab](references/gitlab.md) 使用已认证的 `glab`。相对脚本路径以本技能目录为根；从其他目录调用时使用实际安装目录的绝对路径。输入输出留在目标项目，技能目录只存通用资产。

```text
python scripts/check_patch_manifest.py manifest.json
python scripts/compare_test_results.py compare baseline.json candidate.json
python scripts/github_publish.py publication.json --journal publication-state.json
python scripts/gitlab_publish.py publication.json --journal publication-state.json
```

前两项只读。发布器默认 plan，仍需联网读取目标；只在目标和内容已获授权时加 `--apply`。它只创建 Issue 或同仓库 PR/同项目 MR，并回读标题、正文、仓库身份、状态和分支/SHA；不会推送、上传附件、编辑旧对象、关闭、合并或部署。需要这些步骤时用项目既有工具完成独立授权范围。**防重键只覆盖该键的对象，发布前仍需人工/语义查重。**

CLI 认证沿用已有安全存储；输出使用脱敏证据。平台拒绝是执行限制，应按原错误恢复或报告，不转换操作通道绕过。附件卡失败时核实真实远端对象，交付普通链接并说明卡片限制。

维护脚本时运行 [核心及 GitLab 回归](tests/test_workflow.py) 和 [GitHub 回归](tests/test_github_publish.py)：`python -B -m unittest discover -s tests -v`。它们使用临时 Git 仓库和模拟平台，不触碰真实项目、账号或网络。合成回归与真实平台验收分别报告。
